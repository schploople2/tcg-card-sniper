# Deployment

Railway-specific runbook for shipping TCG Card Sniper. Captures the gotchas we've actually hit so the next deploy doesn't relearn them.

## Services

The Railway project has three services:

| Service | Source | Deploys |
|---|---|---|
| `server` | git, Nixpacks autodetect (Node 20) | **auto** on push to `main` |
| `client` | manual `railway up`, served via Caddy | **manual** — see below |
| `Postgres` | Railway managed | n/a |

## Deploying the server

Push to `main`. Railway picks up the commit, runs the Nixpacks build (`pnpm install --force` → `prisma generate` → `pnpm --filter server build`), then `prisma migrate deploy` + `node dist/index.js` at start. Healthcheck path is `/api/health`.

Verify after deploy:
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://server-production-ad17.up.railway.app/api/health
# → 200
```

## Deploying the client

Client deploys are **manual** — it shares no source-of-truth with the server's Nixpacks config, and Railway's auto-deploy doesn't know to scope to `client/`. Run from a clean working tree:

```bash
RAILWAY_CALLER="skill:use-railway@1.2.1" \
  railway up ./client --path-as-root --service client --detach
```

Wait for the build logs URL to come back, then watch it until you see "Healthcheck succeeded". The client serves at https://poke-sniper.up.railway.app.

## Recurring gotchas (read these)

### Node 20 is mandatory

`cheerio@1` pulls in `undici@7`, which references the Node-20 `File` global at module load. Node 18 hard-crashes with `ReferenceError: File is not defined` the moment `prisma generate`'s output is required.

Defenses:
- `engines.node >= 20.0.0` in root `package.json` (Nixpacks honors this for autodetect)
- `NIXPACKS_NODE_VERSION=20` set as a Railway env on `server` (backstop)

If you see `ReferenceError: File is not defined` in deploy logs, that's this. Check both knobs above.

### Prisma keeps trying to drop the trgm indexes

`Card.name_trgm_idx` and `Card.setName_trgm_idx` are created via raw SQL (Postgres trigram extension) — Prisma's schema language can't model them. Every time you run `prisma migrate dev --create-only`, the generated SQL begins with:

```sql
-- DropIndex
DROP INDEX "Card_name_trgm_idx";
-- DropIndex
DROP INDEX "Card_setName_trgm_idx";
```

**Strip both `DROP INDEX` statements** from the generated `migration.sql` before applying. We've hit this twice (push_subscription + sold_comp migrations).

### Migrations on prod

- `prisma migrate deploy` runs as part of the startup script; never run `migrate dev` against prod
- Create new migrations with `prisma migrate dev --create-only --schema=../prisma/schema.prisma`, strip the trgm drops, then apply with `prisma migrate deploy --schema=../prisma/schema.prisma` (or just push and let prod apply on the next deploy)

### Manual client deploy quirks

- Always include `--path-as-root` so only `client/` is the build context — otherwise Nixpacks picks up the server's `package.json` and builds the wrong thing
- `client/package-lock.json` will be regenerated by Caddy's `npm ci` if it drifts from `client/package.json`. If you add a client dep with pnpm and don't commit the regenerated lockfile, the next manual deploy fails. Either commit the lockfile or delete it (Caddy will regenerate cleanly).

## Rolling back

Open the Railway dashboard for the affected service → Deployments tab → click any prior SUCCESS deployment → "Redeploy". This re-runs that exact build artifact. Prefer this over a `git revert` push when the regression is purely runtime (no schema change).

If the regression involved a migration, you need to either:
1. Forward-fix with a new migration (preferred), or
2. Manually run the down-migration SQL against prod, then redeploy the prior server version

Prisma doesn't generate down migrations — write them by hand if needed.

## Setting / inspecting env vars

```bash
# Read all envs for a service (kv form)
RAILWAY_CALLER="skill:use-railway@1.2.1" \
  railway variables --service server --kv

# Set without triggering a redeploy
RAILWAY_CALLER="skill:use-railway@1.2.1" \
  railway variables --service server --set "FOO=bar" --skip-deploys
```

## Notes on costs

- **Anthropic Vision** is the dominant ongoing cost; capped per-user via `OCR_DAILY_IMAGES_PER_USER`. The auto-OCR sweep cron caps at 5 lots × 6 images per tick = $0.09/hr worst case
- **ScrapingBee** is the second; 25 credits/scrape × 24h cache means a single-user app comfortably fits the free tier
- **Railway** itself is the third; ~$5/mo for the hobby tier covers all three services
